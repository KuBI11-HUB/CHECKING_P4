# GRANTED — Database Guide

How to build the GRANTED database from scratch, what every table and column is for, and how to fix the usual problems.

- **Database name:** `granted_db`
- **Engine:** MySQL / MariaDB (the one that comes with XAMPP), charset utf8mb4 through PDO
- **Size:** 9 tables (Phases 1–5)
- **Files you need:** `database/granted_schema.sql` (fresh install), or the applicable migration files (existing database)
- **Where these files live:** `database/` inside the project, which is in GitHub.

---

## 1. What you need

- Windows with **XAMPP** with **PHP 8.1 or newer** (the Google library used for email needs it). Apache and MySQL both have to run.
- The project folder `GRANTED` (the zip from the team).
- A browser. Nothing else — phpMyAdmin comes with XAMPP.

---

## 2. Set up from scratch (do these in order)

### Step 1 — Start XAMPP
Open the **XAMPP Control Panel** and click **Start** on **Apache** and **MySQL**. Both should turn green.

### Step 2 — Put the project in the right folder
Copy the project into `C:\xampp\htdocs\` so the path is:

```
C:\xampp\htdocs\GRANTED\
```

> **The folder must be named exactly `GRANTED`** (capital letters). Links such as `/GRANTED/admin/dashboard.php` are written into the code. A different folder name breaks navigation.

### Step 3 — Import the schema
1. Open **http://localhost/phpmyadmin**.
2. On the home screen, click the **Import** tab (top of the page, not inside a database).
3. Click **Choose File** and pick `GRANTED\database\granted_schema.sql`.
4. Click **Import** at the bottom.

The file creates `granted_db` by itself, creates all 9 tables, and adds two starter rows: the admin user and one scholarship type called *Academic Scholarship*.

### Step 4 — Check the tables
In phpMyAdmin's left panel, click `granted_db`. You should see exactly these 9 tables:

`documents`, `evaluations`, `grades`, `notifications`, `renewal_decisions`, `rules`, `scholars`, `scholarship_types`, `users`

If you see fewer, stop and read [Section 9](#9-troubleshooting).

### Step 5 — Give the admin a real password
The admin row from the import has a placeholder instead of a password hash, so nobody can log in yet.

**5a. Make a hash.** Open **Command Prompt** (press the Windows key, type `cmd`, Enter) and run:

```
C:\xampp\php\php.exe -r "echo password_hash('admin123', PASSWORD_DEFAULT);"
```

It prints one long line starting with `$2y$10$` (60 characters). Copy the whole line.

**5b. Save it.** In phpMyAdmin click `granted_db` → **SQL** tab, paste this with your hash in place of the placeholder, then click **Go**:

```sql
UPDATE users
SET password_hash = 'PASTE_YOUR_HASH_HERE'
WHERE email = 'admin@granted.local';
```

> The app has no "change password" page yet. To change any password later, repeat 5a with the new password and run the `UPDATE` above.

### Step 6 — Check the database connection settings
Open `GRANTED\config\database.php`. XAMPP's defaults already match:

```php
define('DB_HOST', 'localhost');
define('DB_NAME', 'granted_db');
define('DB_USER', 'root');
define('DB_PASS', '');
```

**Do not edit this file to add a password.** It is committed to GitHub, so a password written here would be public. If your MySQL `root` user has a password, copy `config/database.local.example.php` to `config/database.local.php` and put it there. That file is git-ignored and stays on your computer only.

**Current term.** `config/app.php` holds `CURRENT_SCHOOL_YEAR` and `CURRENT_SEMESTER` (default `2026-2027` / `1st`). Rules, grades and documents are evaluated for that term only. When a new semester starts, change those two lines (or override them in `config/app.local.php`), then run `C:\xampp\php\php.exe tools\reevaluate_all.php` so every scholar's status is recalculated for the new term.

### Step 7 — Check the uploads folder
`GRANTED\uploads\documents\` must exist. XAMPP lets PHP write to it by default. Scholars' uploaded files are saved here, not in the database.

### Step 8 — Log in and confirm
Go to **http://localhost/GRANTED/auth/login.php**.

- Email: `admin@granted.local`
- Password: `admin123` (or whatever you hashed in Step 5)

You should land on the **Admin Dashboard**. If you do, the database is working.

### Step 9 — Add the scholarship types your team needs
The import only creates *Academic Scholarship*. The feature list also calls for **CHED** and **DOST**. Log in as admin → **Scholarship Types** and add them. (Add them in the app, not in phpMyAdmin.)

## 3. Tables at a glance

| # | Table | What it stores | Written by | Used by the app today? |
|---|-------|----------------|------------|------------------------|
| 1 | `users` | Login accounts (admin and scholars) | Admin enrolls a scholar | Yes |
| 2 | `scholarship_types` | CHED, DOST, Academic, etc. | Admin | Yes |
| 3 | `rules` | Requirements per scholarship type and term | Admin | Yes |
| 4 | `scholars` | Scholar profile plus the **calculated** GPA, units, status | Admin (profile), rule engine (calculated fields) | Yes |
| 5 | `grades` | Subject grades and units per term | Admin | Yes |
| 6 | `documents` | Uploaded compliance documents and their review result | Scholar (upload), admin (review) | Yes |
| 7 | `evaluations` | Result of each rule for each scholar (rule-by-rule breakdown) | Rule engine only | Yes |
| 8 | `notifications` | Every email the system sends, shown as the scholar's notification history | System (status changes and deadline reminders) | **Yes** (the scholar-facing history page comes later, task 4.6) |
| 9 | `renewal_decisions` | The office's actual renewal decision and remarks | Admin (Phase 5) | **Created, not used yet** |

`notifications` is filled automatically whenever a scholar's status changes or a deadline reminder is created, even when email sending is switched off (those rows stay `QUEUED`). `renewal_decisions` exists so the structure is ready; its PHP code is built in Phase 5, so seeing it empty is normal.

### How the tables connect (foreign keys)

| Child column | → | Parent column |
|--------------|---|---------------|
| `rules.scholarship_type_id` | → | `scholarship_types.id` |
| `scholars.user_id` | → | `users.id` |
| `scholars.scholarship_type_id` | → | `scholarship_types.id` |
| `grades.scholar_id` | → | `scholars.id` |
| `documents.scholar_id` | → | `scholars.id` |
| `documents.reviewed_by` | → | `users.id` (the admin who reviewed) |
| `evaluations.scholar_id` | → | `scholars.id` |
| `evaluations.rule_id` | → | `rules.id` |
| `notifications.scholar_id` | → | `scholars.id` |
| `notifications.rule_id` | → | `rules.id` (optional) |
| `renewal_decisions.scholar_id` | → | `scholars.id` |
| `renewal_decisions.decided_by` | → | `users.id` (the admin) |

Read it as: *a row in the child table must point to a row that exists in the parent table.* MySQL refuses to break that (see [error 1451 / 1452](#9-troubleshooting)).

```
scholarship_types ──< rules
        │
        └──< scholars >── users
                │
                ├──< grades
                ├──< documents
                ├──< evaluations  (each also points to a rule)
                ├──< notifications  (a reminder also points to a rule)
                └──< renewal_decisions
```

## 5. Rules of the database (read before editing anything)

1. **Calculated status vs. office decision.** `scholars.current_gpa`, `current_units` and `current_status` are written only by the rule engine (`includes/rule_engine.php`). Admins and developers do not set them by hand. The office's real decision goes in `renewal_decisions`, a separate table. This is a requirement in FEATURES.pdf.
2. **Grading scale.** Lower is better (1.00 best, 5.00 failing), so a rule "GPA `<=` 2.00" means *passing*. GPA is the unit-weighted average: `SUM(grade × units) ÷ SUM(units)` over the scholar's `grades` rows. `current_units` is `SUM(units)`. Only grades of the **current term** (`CURRENT_SCHOOL_YEAR` + `CURRENT_SEMESTER` in `config/app.php`) are counted, and only rules and documents of that term are evaluated.
3. **DOCUMENT rules match by exact text.** `rules.threshold_value` and `documents.document_type` must be identical, including spelling, capitals, and spaces. The newest upload of that type is the one that counts.
4. **Never delete; deactivate.** Rules are turned off with `is_active = 0`. Foreign keys block deleting anything that other tables still use.
5. **One row per scholar and rule in `evaluations`.** The engine overwrites it; don't insert rows there manually. Rows are never deleted, so old rows for deactivated or past-term rules stay in the table. The app hides them by joining to `rules` with `is_active = 1` and the current term, and any new query that shows results must do the same.
6. **Passwords are hashes only.** Scholars never register themselves. The admin enrolls them, which creates the `users` row and the `scholars` row together.
7. **Exact term spelling.** `school_year` looks like `2026-2027`. `semester` is exactly `1st`, `2nd`, or `Summer`.
8. **Files are not in the database.** `documents.filepath` is only a file name. The files live in `uploads/documents/`. A database export doesn't include them.
9. **Timestamps fill themselves.** Don't set `created_at`, `uploaded_at`, and so on by hand.
10. **Known issue, don't fix by hand.** The app currently escapes text *before* saving, so `Ana O'Brien` is stored as `Ana O&#039;Brien`. That's a bug in the PHP code, planned for the Phase 7 security pass. Don't clean the data in phpMyAdmin.

## 6. Which action writes to which table

| Action in the app | Tables changed |
|-------------------|----------------|
| Admin adds a scholarship type | `scholarship_types` |
| Admin adds a rule / deactivates a rule | `rules` (`is_active` set to 0 when deactivating), then every scholar on that scholarship type is re-evaluated (`scholars`, `evaluations`, maybe `notifications`) |
| Admin enrolls a scholar | `users` (role = scholar) and `scholars` |
| Admin saves a grade | `grades`, then the engine updates `scholars` (GPA, units, status) and `evaluations`; a status change also adds a `notifications` row |
| Scholar uploads a document | `documents` (status = Pending Review) |
| Admin verifies or rejects a document | `documents` (status, remarks, reviewer), then the engine updates `evaluations` and `scholars.current_status` |
| Status changes, or the daily reminder script runs | `notifications` |
| Admin records the renewal decision *(Phase 5)* | `renewal_decisions` |

## 7. Useful SQL (phpMyAdmin → `granted_db` → SQL tab)

These only read data, so they're safe to run.

**Row count in every table**
```sql
SELECT 'users' AS tbl, COUNT(*) AS n FROM users
UNION ALL SELECT 'scholarship_types', COUNT(*) FROM scholarship_types
UNION ALL SELECT 'rules', COUNT(*) FROM rules
UNION ALL SELECT 'scholars', COUNT(*) FROM scholars
UNION ALL SELECT 'grades', COUNT(*) FROM grades
UNION ALL SELECT 'documents', COUNT(*) FROM documents
UNION ALL SELECT 'evaluations', COUNT(*) FROM evaluations
UNION ALL SELECT 'notifications', COUNT(*) FROM notifications
UNION ALL SELECT 'renewal_decisions', COUNT(*) FROM renewal_decisions;
```

**Can the accounts log in? (the hash must start with `$2y$10$`)**
```sql
SELECT id, email, role, LEFT(password_hash, 7) AS hash_starts_with FROM users;
```

**All scholars with their calculated status**
```sql
SELECT s.id, s.full_name, u.email, st.name AS scholarship,
       s.current_gpa, s.current_units, s.current_status
FROM scholars s
JOIN users u ON u.id = s.user_id
JOIN scholarship_types st ON st.id = s.scholarship_type_id;
```

**Rule-by-rule breakdown for one scholar (change the `1` to the scholar's id)**
```sql
SELECT r.rule_type, r.operator, r.threshold_value, e.result, e.evaluated_at
FROM evaluations e
JOIN rules r ON r.id = e.rule_id
WHERE e.scholar_id = 1
ORDER BY r.id;
```

**Documents waiting for review**
```sql
SELECT d.id, s.full_name, d.document_type, d.status, d.uploaded_at
FROM documents d
JOIN scholars s ON s.id = d.scholar_id
WHERE d.status = 'Pending Review'
ORDER BY d.uploaded_at;
```

**Calculated status next to the office's decision (works once Phase 5 is built)**
```sql
SELECT s.full_name, s.current_status AS calculated_status,
       rd.decision AS office_decision, rd.remarks
FROM scholars s
LEFT JOIN renewal_decisions rd
       ON rd.scholar_id = s.id AND rd.school_year = '2026-2027' AND rd.semester = '1st';
```

## 8. Starting over, and upgrading an existing database

**Clear test data but keep the admin, scholarship types and rules**
```sql
SET FOREIGN_KEY_CHECKS = 0;
TRUNCATE notifications;
TRUNCATE renewal_decisions;
TRUNCATE evaluations;
TRUNCATE documents;
TRUNCATE grades;
TRUNCATE scholars;
DELETE FROM users WHERE role = 'scholar';
SET FOREIGN_KEY_CHECKS = 1;
```
Then delete the files inside `uploads\documents\` by hand, or the old uploads stay on disk.

**Wipe everything and re-import from scratch**
```sql
DROP DATABASE granted_db;
```
Then repeat Steps 3–5 of [Section 2](#2-set-up-from-scratch-do-these-in-order). This deletes all data in the database.

**You already have the Phase 1–3 database (7 tables) and just need the new parts**
Don't re-import the full schema. In phpMyAdmin click `granted_db` → **Import** → choose `database/phase4-5_migration.sql`. It adds `notifications`, `renewal_decisions` and the `rules.due_date` column, keeps all your data, and is safe to run twice.

**Enable duplicate-upload protection on an existing database**
Import `database/document_submission_dedup_migration.sql` once in phpMyAdmin after the other migrations. It adds a unique submission token to new document uploads and preserves existing documents. Fresh databases already have this column and do not need this migration.

## 9. Troubleshooting

| What you see | Why | Fix |
|--------------|-----|-----|
| **"Database connection failed: … Unknown database 'granted_db'"** | The schema wasn't imported | Do Step 3. |
| **"… Access denied for user 'root'"** | `DB_PASS` in `config/database.php` doesn't match your MySQL password | Fix `DB_PASS`. XAMPP's default is empty. |
| **"… Connection refused"** | MySQL isn't running | Start MySQL in the XAMPP Control Panel. |
| **MySQL turns red and won't start in XAMPP** | Another MySQL is already using port 3306 | Open Windows **Services**, stop the other MySQL service, then start MySQL from XAMPP. |
| **Import says `#1050 Table 'users' already exists`** or **`#1062 Duplicate entry 'admin@granted.local'`** | You imported the full schema into a database that already has tables | Use the migration file if you want to keep data, or drop the database and re-import (Section 8). |
| **Admin login says wrong email or password** | Step 5 was skipped, so the hash is still the placeholder | Run the "Can the accounts log in?" query (Section 7). If it doesn't show `$2y$10$`, redo Step 5. |
| **Pages 404, or buttons go to the wrong place** | The folder isn't named exactly `GRANTED` | Rename it to `GRANTED` inside `htdocs`. |
| **`#1451 Cannot delete or update a parent row`** | Other rows still depend on that row, and the foreign keys are protecting your data | Deactivate instead of deleting (`is_active = 0` for rules). To delete test data, use the clear script in Section 8. |
| **`#1452 Cannot add or update a child row`** | You inserted an id that doesn't exist (e.g. a `scholar_id` with no matching scholar) | Check that the parent row exists first. |
| **Upload fails** | `uploads\documents\` is missing or not writable, or the file isn't PDF/JPG/PNG | Create the folder and try a PDF, JPG, or PNG. |
| **"View file" opens a broken link** | You copied the database to another computer without the `uploads\documents\` files | Copy those files too. |
| **A scholar's status shows PENDING with a passing GPA** | A DOCUMENT rule is still waiting for upload or admin review | That's correct behavior. Check the rule-by-rule query in Section 7. |

## 10. Working as a team

- **Each person has their own database.** Data isn't shared automatically. To give a teammate your data: phpMyAdmin → `granted_db` → **Export** → *Quick* → *SQL*, send them the file, and they import it into an empty `granted_db`. Copy `uploads\documents\` too.
- **Never change a table's structure only in phpMyAdmin.** Put every change in a new numbered `.sql` file inside `database/` (for example `phase6_….sql`), tell the team to run it once, **and** update `granted_schema.sql` so a fresh install matches. The rule: *fresh schema* and *old schema + all migrations* must end up identical.
- **Keep the project and the `.sql` files in Git (GitHub) or a shared drive**, not only on one laptop or one account.
